# Proposal：C2 多用户执行隔离、容量治理与恢复验证

## Why

C1 解决身份与授权入口后，`CommandDeliveryService.deliverDue()` 仍一次取出到期命令并逐个直接 `deliver`，`NativeProjectionPoller.projectDue()` 同样遍历 Binding；SSE 单实例线程池固定 4、连接数 100；用户总预算已有 DB 预留机制，但未覆盖登录后的请求速率/并发任务配额。当前多实例测试主要是同 JVM 双 Spring Context，不能以此宣称跨进程接管完成。

## Scope

- **先通过可控慢 SDK Stub 验证是否真的阻塞**，再决定是否改造成“短事务领取 + 有界执行池 + 按用户公平调度”；禁止只凭静态报告改底层。
- 为会话、模型/工具、Worker、SSE 建立按用户的并发/速率限额，并保证不同用户互不挤占；优先复用已有预算和租约。
- 实测跨独立进程恢复与 SDK 本地 workspace 的作用；条件不成立就将 V1 部署限制在单业务执行实例，不擅自构建跨机器共享文件系统。
- 清理生产可触发的 `Runtime.halt(137)` 故障注入入口，并隔离 SDK 文本异常匹配。
- 保持消息幂等、原生 SDK 命令 ID、计划 DAG 与审批账本语义不变。

## Non-goals

- 不改变模型 Provider 体系，不引入 Kafka/Redis/MQ，不按 Agent 角色拆成多个服务。
- 不承诺任意规模自动扩容；执行结果以明确的压测和恢复试验为准。
- 不自动修复 UNKNOWN 外部写入，也不自动清除任务执行账本。

## Dependencies / Acceptance

- 必须在 C1 完成并经过两用户真实 HTTP 安全验证后开始。
- 通过 A02/A03/A07/A11/A12 与多用户并发、过载、取消优先级和重启接管测试；单任务慢响应不能使另一个用户所有新命令不可处理。
- 真实负载容量必须用测量数据描述，未经压测不得声称“支持 100/1000 在线用户”。
