## 2026-11-06：回复显示不流畅与模型异常恢复

状态：待排查、待修复，尚未验收。以下区分用户反馈与待验证原因，不代表已定位根因。

### 1. 回复逐字跳出、卡顿和反复渲染

- 用户反馈：回复像一个字一个字蹦出来，中间卡顿，能明显看到页面重新渲染的过程。
- 排查范围：模型原始分片间隔、后端事件合并与推送频率、前端文本更新频率、Markdown 重算、自动滚动，以及流式正文切换为最终正文时是否重建内容。
- 改进目标：保持及时显示，同时按短时间窗口合并更新；避免每个字符触发整段 Markdown 和整页重算。最终正文接替流式内容时保持稳定，不闪烁、不重复、不丢字。
- 验收：长文本、代码块、表格分别测试；记录首段出现时间、更新间隔及页面性能。刷新或重连后正文完整，失败时也不把已有内容突然清空。

### 2. 模型异常后，SDK 重试与平台恢复需要配合

- 用户反馈：本次“开启两个任务并行分析这两个文档，把文档内容梳理归纳一下”最终显示“回答服务暂时异常，未能完成这次回答。你的消息已保留。”，页面仅提供“复制原消息”。附件为“车辆状态流转流程图.md”和“agentsquad-chat-upload.txt”。
- 用户初步判断：模型返回异常。仍需用该请求的日志、模型错误与执行记录确认实际原因及两个任务是否创建、开始和完成。
- 排查范围：AgentScope 当前版本实际重试配置、可重试错误范围与次数；平台命令重试、任务恢复、超时判断和最终失败时机；是否出现 SDK 尚在重试而平台已判失败，或两层同时重试造成重复执行。
- 改进目标：明确每层负责的失败。模型短暂异常由 SDK 在有界次数和总时限内处理；平台负责 SDK 最终失败后的业务恢复及进程中断恢复。恢复不得重复创建任务、重复执行已成功的工具副作用或覆盖已完成结果；部分输出后的重试要明确替换或续接规则，不能简单拼接新旧回答。
- 用户体验：恢复期间用简短文字说明“服务暂时不稳定，正在重试”；恢复耗尽才显示最终失败。提供与实际能力匹配的重试或继续入口，保留附件、原始要求和已完成步骤；不得只让用户复制原消息，也不得把仍可恢复的执行提前显示为失败。
- 日志要求：同一个请求可查到模型每次尝试、失败原因、SDK 重试结束、平台恢复决策、已完成步骤复用和最终结果；携带 traceId、executionId 及相关 taskId/jobId，保留必要异常堆栈，不记录密钥和完整文档内容。
- 验收：覆盖首次调用暂时失败后成功、持续失败、已输出部分正文后断流、一个并行任务成功另一个失败、页面断开重连、执行进程重启。确认无重复任务与副作用，成功内容保留，前端状态与后台实际执行一致。

### 处理顺序

1. 定位本次真实请求，串起模型、SDK、平台和页面的时间线。
2. 明确重试与恢复分工、次数和总时限，再修复提前失败或重复恢复问题。
3. 测量流式显示链路，调整合并更新与页面渲染。
4. 用故障注入验证恢复边界，再以真实模型和双文档并行请求复验。

证据来源：本地 `/tmp/agent-squad-server-local.log`，以及当前源码和本机 AgentScope `2.1.0-BETA1` sources.jar。以下为排查结果，尚未修复或完成故障注入复验。

1. **模型断流已确认，供应商断流原因未确认。** 13:30:18.478 消息受理，18.657 原生命令投递，43.597 记录模型错误。异常链为 OpenAIException → HttpTransportException → IOException → EOFException（chunked transfer encoding / EOF reached while reading）。43.856 回复进入 FAILED。不能据此断言模型供应商内部故障，也不能认定是浏览器断线导致模型断流。
2. **SDK 模型重试当前被明确关闭。** MasterAgent 与 WorkerFactory 均配置 `modelExecutionConfig.maxAttempts(1)`。SDK 的 ModelUtils 支持可配置退避重试，但发出可见内容后不再原地重试，以避免重复输出。因此“SDK 自带重试”不等于本项目当前已经启用，更不能简单把次数改大后就认为覆盖了断流恢复。
3. **平台恢复被错误分类挡住。** ModelFailureClassifier 识别连接失败、SocketTimeoutException 和 TimeoutException，却漏掉本次流传输中的 IOException/EOFException，最终落为 INTERNAL / EXECUTION_INTERRUPTED。ExecutionFailureService.queueTransientRetry 只接受 SERVICE_TRANSIENT，所以本次未进入自动恢复。后续修复应限定在模型传输异常链内识别断流，避免把本地文件读写失败一概当成可重试模型错误。
4. **没有重试按钮也与分类有关。** ExecutionFailureMapper.retryAllowed 只放行 SERVICE_TRANSIENT 或 MODEL_BILLING_UNAVAILABLE，并检查预算、未决副作用、交互和后续重试。本次 INTERNAL 不符合条件，页面只剩复制原消息。不能为了出现按钮而绕过副作用和幂等保护。
5. **SSE 还有独立的异步鉴权问题。** 13:30:43.866 同会话 events 请求出现“网关身份断言无效”；日志含 AsyncContextImpl 内部重派发。UserContextInterceptor 每次 preHandle 都重新验证签名，SignedIdentityVerifier 的断言有效期约 30 秒，没有复用同一请求首次验证的身份。高度怀疑长连接异步重派发时重复校验过期断言；需用超过有效期的真实异步请求复现，不能把提高有效期作为正式修复。应区分新请求与已验证请求的异步派发，并继续保留账号停用与会话访问检查。
6. **SSE 异常处理协议错误已确认。** 上述异常之后，通用异常处理尝试返回 ApiResult，而响应已是 text/event-stream，触发 HttpMessageNotWritableException；随后又出现 response committed 后 sendError 失败。事件流已开始后需要按流协议结束，不能再包装普通 JSON。
7. **卡顿相关代码路径已确认，性能影响尚未测量。** ReplyPreviewBuffer 每 50ms 最多推送一次累积全文，没有固定字符数门槛；前端每次预览更新都调用 SafeMarkdown.blocks 重新解析完整正文，并在 MessageThread 的 revision watcher 中读取滚动高度、更新滚动位置。没有发现前端人工逐字播放定时器。逐字感可能来自上游小分片及当前更新节奏，具体耗时仍需浏览器性能记录。
8. **断线和最终落文容易造成视觉跳变。** conversations.ts 在 onerror、scheduleReconnect 和 connect 中清空预览；临时正文和持久正文又使用不同的 article 列表与 key。这会产生正文消失、重建的条件，不能只靠合并推送频率解决。
9. **两条连接提示重复有明确来源。** refreshSnapshot 失败写入 chat.error，SSE 失败写入 connection=offline；MessageThread 独立显示两者，于是截图中红色错误条与“正在重新连接”同时出现。应统一连接反馈，并区分发送结果不明、历史读取失败、事件流重连、执行失败；已确认受理的消息不能继续让用户误以为未提交。
