# AgentSquad 迭代总结与架构升级设计

> 本文是当前阶段的正式总结与后续架构基线。它合并阶段性调研结论，不代表所有目标能力已经完成。
>
> 更新日期：2026-11-11
> 分支：`feat/20261103_log_optimize`
> 调研基线：AgentScope Java 2.1.0-BETA1（具体结论以对应源码审计记录为准）

## 1. 项目定位与阶段目标

AgentSquad 是面向多用户的 Agent 产品底座。当前优先做好一期智能客服：用户可以像使用普通聊天产品一样持续对话，Agent 能结合知识、工具和上下文处理问题；遇到复杂问题时，再由 Master 组织多个执行单元完成工作。

当前阶段不是一次性建设通用 Agent 平台、平台接入市场或通用 DAG 调度器。先把客服场景的会话、运行、持久化、恢复、实时反馈和权限边界打牢，再逐步扩展复杂任务与多平台接入。

核心原则：

1. 优先使用 AgentScope 原生能力，不重复实现 Agent Runtime。
2. 产品业务与 Agent 执行机制分层，产品会话不等于 AgentSession。
3. 运行记录持久化不等于任务能够跨进程恢复，必须区分数据保存、执行接管和业务补偿。
4. Redis 通知可以丢失，业务事实不能丢失；通知只负责唤醒，不负责授权或确认业务成功。
5. 先验证再迁移，架构目标不直接等同当前实现。

## 2. 迭代过程与主要收敛

### 2.1 从现有实现审计开始

早期工作集中在多用户身份、会话、消息、Worker、任务计划、执行恢复和日志观测等能力。随后发现，如果继续在现有 Worker/DAG 结构上叠加功能，容易重复建设 AgentScope 已经提供的会话、事件、工具和恢复机制。

因此调整为：先审计现有代码和 AgentScope 指定版本源码，逐项确认原生能力、平台已接入能力和缺口，再决定保留、替换或补充的部分。

### 2.2 从“统一 Worker”转为按任务性质选择执行方式

调研后明确，原生 SubAgent 与 AgentSession 不是同一种执行模型：

- SubAgent 适合由 Master 按需创建的短期、独立工作，例如并行调查、资料分析和专项推理。
- AgentSession 适合需要独立会话记录、执行控制、输入队列、恢复和持续交互的执行过程。
- 当前 Worker 承担固定业务任务、计划版本隔离、结果验收和故障恢复，不能仅因为原生 SubAgent 更轻量就直接替换。

最终采用混合模式：Master 使用 AgentSession 管理自己的持续会话；在能力和生命周期验证通过后，可使用原生 SubAgent 处理短期子工作；需要持久化、恢复和业务验收的复杂工作继续使用 Worker/独立 Session 路径。

### 2.3 从“Redis 加速”转为明确数据职责

Redis Stream 已接入命令唤醒、事件投影唤醒和跨实例会话通知。调研明确了它们只传递命令或会话引用，不承载权威业务正文，也不授予执行资格。

业务命令、执行记录、原生 Journal 和正式事件仍有 PostgreSQL 持久化来源。Redis 不可用时，系统保留本地派发、数据库扫描、SSE 重连和持久事件补读等补偿路径。

下一步研究重点不是简单把更多内容搬进 Redis，而是测量每次执行造成的数据库读写、事务次数、延迟、Redis 内存与网络开销，并验证 Redis 原生 Store 的故障恢复语义。

### 2.4 从过程日志转向可维护的架构基线

本轮将 AgentScope 原生能力盘点、产品能力评估、一期数据/API 草案、实体关系审查和阶段性研究记录收敛到本文。运行中的专项设计、OpenSpec 变更、验证说明仍保留在各自位置，不将其误删为临时材料。

## 3. 目标架构与职责边界

```text
用户交互层
  客服聊天、会话管理、资源配置、实时事件展示
        |
AgentSquad 产品应用层
  身份与权限、会话目录、Agent Definition、模型/工具/知识资源
  上下文准备、运行适配、事件转换、SSE 交付、任务验收
        |
AgentScope 运行层
  Master AgentSession
  原生 SubAgent（短期并行工作）
  独立 Worker / AgentSession（需要持久执行和业务验收的工作）
  原生事件、输入队列、工具调用、记忆与 Workspace
        |
运行时数据与业务持久层
  Redis：运行时高频数据、通知、消息流（目标扩展需专项验证）
  PostgreSQL：业务事实、任务计划、执行快照、正式结果、审计
  文件/知识存储：附件、正式产物、知识文档及检索索引
        |
外部能力
  LLM、Embedding/Rerank、MCP、业务 API 和受控工具
```

| 模块 | 负责什么 | 不负责什么 |
|---|---|---|
| AgentSquad 产品层 | 用户身份、权限、产品会话、Agent 配置版本、资源治理、结果交付 | 不重新实现 Agent 推理循环和原生 Session |
| AgentScope | Agent 执行、Session 生命周期、原生事件、工具与运行时能力 | 不负责产品用户体系、业务权限和平台配置治理 |
| Master | 理解用户目标、规划、分派、协调、验收和最终答复 | 不直接绕过权限和业务校验执行外部副作用 |
| SubAgent | 短期独立调查、并行分析和局部推理 | 不默认承担需要跨进程恢复的长期任务 |
| Worker | 有明确任务边界、独立执行上下文、结果保存与业务验收的工作 | 不与普通 SubAgent 混为同一生命周期 |
| Redis | 运行时消息、唤醒通知、高频状态的候选存储 | 不作为业务命令和最终结果的唯一事实来源 |
| PostgreSQL | 用户、会话关系、命令、计划、执行快照、结果和审计 | 不应被无差别地用于每个高频运行时心跳 |
| 文件/知识服务 | 文件、正式产物、知识文档、权限和检索资源 | 不与 AgentScope Workspace 的运行目录混为一谈 |

以上是目标逻辑边界，不要求立即拆成微服务。

## 4. AgentScope 原生能力调研结论

### 4.1 AgentSession 是持续交互和恢复的优先基础

重点复用原生能力：

- `submit`：提交新的执行输入。
- `steer`：向当前执行补充要求，实现真正的执行中插话。
- `inject`：注入补充材料。
- `interrupt`：请求中断当前执行。
- `respond`：回答等待中的交互请求。
- `resume`：从已保存的 Turn 继续执行。
- Session Log / Journal：记录执行事件、消息、输入队列及恢复所需信息。

产品层需要将这些能力适配为稳定的业务 API 和公开事件。不能把一次 HTTP 请求、一个 Turn 和一个 Run 简单设计成一一对应关系。

### 4.2 原生 SubAgent 不能直接等同分布式任务系统

调研发现，任务记录持久化、本地 Future 执行和故障检测是不同环节。任务记录保存在 Workspace，不代表其他 JVM 能恢复原 JVM 的本地 Future；审计版本中的默认失联处理是标记失败，而不是从断点自动续跑。

因此，原生 SubAgent 适合短期并行工作，但在证明跨进程恢复、任务隔离、结果验收和异常接管前，不替换当前持久 Worker 路径。

### 4.3 执行资格与业务数据分离

AgentScope Session 的 Writer、Lease、Epoch 和 CAS 用于管理执行资格及防止旧执行者继续提交。它们不意味着业务数据不需要事务，也不意味着所有 `SELECT FOR UPDATE` 都可以删除。

当前 JDBC Store 的版本条件更新属于 CAS 思路。仍需关注 Session 心跳和续租可能带来的数据库写入压力；不能在没有故障演练的情况下随意延长 Lease 或降低续租频率。

### 4.4 记忆与 Workspace

AgentScope 提供 Memory、Workspace、Filesystem 和相关读写接口。平台服务不能依赖某个固定本机目录作为长期记忆的唯一存储。

目标是让 Workspace 的逻辑目录结构与实际存储介质解耦：本机磁盘、共享 KV/JDBC 或受控沙箱均可作为实现选择。具体接入以 AgentScope 原生 Filesystem/Store 扩展为优先，不自行重复造一套文件系统。

产品仍需负责用户隔离、记忆查询入口、知识资源授权、保存策略、生命周期和必要的检索能力。原生 Memory 文件布局也不能直接等同产品级记忆管理功能。

## 5. 当前运行链路与存储边界

### 5.1 命令执行与实时反馈

当前已形成的主要链路：

```text
用户提交消息
  -> PostgreSQL 保存命令和业务事实
  -> Redis Stream 发布 commandId 唤醒引用
  -> 后台重新读取数据库，校验归属、权限、顺序和执行资格
  -> AgentScope AgentSession 执行
  -> 原生 Journal 持久化执行事件
  -> 事件收件与业务状态更新
  -> Redis 发布投影唤醒通知
  -> 消费者补读原生事件并更新业务视图
  -> SSE 向前端交付公开事件
```

关键约束：

- Redis 通知不等于命令已执行，也不授予执行资格。
- 消费者必须重新从数据库核对用户、会话、Binding 和版本信息。
- 重复通知通过版本合并、幂等屏障和持久状态处理。
- 消息 ACK 只确认通知已被持久领取/投递处理，不等待模型生成结束。
- Redis 故障时保留本地派发、持久扫描、事件补读和重连能力。
- 页面 SSE 断开不代表后台执行终止；重连应从持久游标续读。

### 5.2 存储职责

| 数据 | 当前/目标存储 | 说明 |
|---|---|---|
| 用户、产品会话、命令、计划和业务状态 | PostgreSQL | 业务事实来源 |
| AgentScope 原生 Journal、输入队列、检查点和写入者屏障 | 当前为 JDBC Store；Redis Store 是专项候选 | 不应同时维护两份互相矛盾的执行事实 |
| Redis 命令/控制/投影通知 | Redis Streams | 传引用和唤醒信号，可补偿 |
| 跨实例会话通知与正文预览 | Redis Pub/Sub 等通知通道 | 可丢失，正式结果仍以持久记录为准 |
| 用户附件和正式产物 | 文件/对象存储 | 按既有文件协议管理 |
| 知识文档与向量索引 | 独立知识资源层 | 权限和索引生命周期由产品治理 |

当前 `docs/runtime-database-storage.md` 记录了 AgentScope 运行日志使用数据库存储的具体实现和迁移约束；Redis Journal 仍是候选方向，不宣称已经迁移完成。

## 6. 一期客服产品的数据与接口原则

产品会话和 AgentScope Session 是两个对象。产品会话保存用户归属、标题、Agent Definition 版本、归档状态和稳定的原生 Session 关联；AgentScope 管理 Turn、Run、执行事件、输入队列和恢复状态。

Agent Definition 应采用可追溯版本。创建会话时固定使用的配置版本，后续修改 Agent 配置不应悄悄改变既有会话的执行定义。

优先建设的产品数据包括：

- 用户身份与权限。
- Agent Definition 及不可变配置版本。
- Conversation 产品会话目录。
- 必要的模型、工具/MCP、Skill、知识库和文件资源元数据。

不默认复制以下原生数据：

- Agent Turn / Run / Session Log。
- Agent 输入队列和 Checkpoint。
- 完整原生事件日志。
- AgentScope 原生 Memory 的全部内容。

只有当产品查询、审计、权限、保留或性能确实需要时，再从原生日志构建产品读模型，且明确唯一事实来源。

接口围绕业务动作设计：创建/查询会话、提交问题、追加要求、注入材料、订阅事件、停止执行、继续执行、回答待办交互。HTTP 受理成功只表示请求已保存，不代表 Agent 已完成。

## 7. 已落地能力与证据边界

当前分支已有以下实现或专项验证记录：

1. 多用户身份与产品会话基础。
2. 命令持久化、后台领取和 Redis Stream 唤醒。
3. Redis 投影唤醒与原生事件补读。
4. 跨实例会话通知和公开正文预览的验证路径。
5. AgentScope JDBC 原生运行日志存储及旧本地日志导入说明。
6. 任务步骤状态、失败收尾、部分完成和逐项验收规则。
7. 观测设计与分阶段任务清单。
8. AgentScope 学习实验室模块及 IDEA 共享调试配置。

以上不代表所有能力均已完成生产级验收。特别是跨机器/跨进程真实部署、Redis 全量数据丢失、真实模型复杂长流程、完整故障恢复矩阵和高并发容量，仍需要单独验证。

## 8. 尚未收敛的问题与下一阶段

### P0：AgentSession 完整生命周期

- 把 submit、steer、inject、interrupt、respond、resume 的状态变化与产品 API 对齐。
- 明确 SSE 断线续读、事件顺序、重复事件、预览和正式终稿的关系。
- 验证多实例执行资格接管、长时间 GC、节点暂停和网络分区。
- 修复并验收异步 SSE 鉴权、错误处理和模型 EOF 断流分类等已记录问题。

### P0：Redis / PostgreSQL 存储评估

- 对 AgentScope 原生 Redis Store 做独立 PoC，不直接切换生产存储。
- 验证 Redis 持久化、复制、主从切换、CAS、Lease、Journal 完整恢复。
- 统计 1000 / 5000 / 10000 活跃会话下的心跳、CAS、事件、数据库事务、Redis 内存和网络开销。
- 量化每个 Agent 事件引起的数据库读写次数和端到端延迟。
- 形成数据迁移、回退、归档和补偿方案。

### P1：Master 与 SubAgent 协作

- 评估启用 Master 原生 SubAgent，保留 Worker 作为长任务执行单元。
- 明确短期 SubAgent 与持久 Worker 的创建、取消、结果返回和异常边界。
- 验证 Worker 完成后如何可靠唤醒 Master，以及计划版本变化时如何隔离旧结果。
- 统一权限、模型选择、预算和执行上下文的传递规则。

### P1：记忆、知识与 Workspace

- 继续使用 AgentScope 原生 Memory / Filesystem / Store 能力。
- 明确用户记忆、会话记忆、平台知识库的区别和权限范围。
- 设计持久化、查询、更新、归档和删除策略。
- 验证无本机持久磁盘环境下的共享存储或沙箱方案。

### P2：观测与测评

- 先打通请求到命令、Session、模型、工具、Worker、结果发布的全链路追踪。
- 观测数据不能阻塞业务，不能记录完整敏感 Prompt、凭据和大对象。
- 再建立固定题库、规则检查、人工校准和模型对比。
- 用真实数据验证质量、成本、耗时和恢复能力，不以单次成功代替系统验收。

## 9. 明确不做的事情

1. 不为了架构统一而重写已经具备业务价值的 Worker/任务验收链路。
2. 不把普通 SubAgent 当作具备跨 JVM 自动恢复能力的分布式任务。
3. 不因为 AgentScope 使用 CAS 就全局删除业务锁和事务。
4. 不把 Redis 当成业务命令、最终答案或审计记录的唯一存储。
5. 不在没有容量与故障证据时，把所有 Journal 一次性迁移到 Redis。
6. 不重复建设 AgentScope 已提供的推理循环、Session Log、输入队列和基础执行控制。
7. 不在一期提前建设通用平台接入市场和完整 DAG 调度产品。
