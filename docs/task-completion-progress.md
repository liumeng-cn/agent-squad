# 任务失败收尾与步骤展示

## 已实现规则

| 实际情况 | 系统处理 | 页面说明 |
| --- | --- | --- |
| 前置工作仍在执行 | 下游保持 BLOCKED | 等待前一步完成 |
| 工作恢复受限 | 保留 RECOVERY_BLOCKED，交给 Master 重新安排 | 遇到问题，需要重新安排 |
| 前置工作明确失败 | 当前计划未执行的硬依赖下游递归 SKIPPED | 前一步失败，这一步未执行 |
| 其他独立工作还在执行 | 继续执行，阻止提前发布完成结果 | 各步骤分别显示状态 |
| 已换成新计划 | 只统计当前版，旧结果不得激活新依赖 | 读取当前计划步骤 |

BLOCKED、RECOVERY_BLOCKED、等待输入、等待审批、恢复中、结果核对中及停止中均阻止提前完成。结束数量不作为成功数量，页面只将 SUCCEEDED 计入“已完成”。可选失败由必要验收结论决定是否影响整体成功，必要工作失败不能报全部完成。

## 明确放弃无法恢复的工作

Task Master 可调用 `abandon_failed_job`，参数为 `jobId`、`expectedPlanVersion`。用户和会话来自可信运行上下文，不能通过参数指定其他用户或目标。

服务在事务内锁定归属、目标、当前计划及节点，只允许当前计划的 RECOVERY_BLOCKED 转为 FAILED。正在执行、等待恢复命令、未处理交互、外部效果未核实、待处理用户修改或控制均拒绝。失败状态、下游跳过、公开事件与协调通知一起提交；重复调用不重复产生事件。新计划生效后，旧决定被拒绝。

这不是强制结束活跃任务的入口，也不能绕过未知外部结果检查。Master 应优先考虑重新安排工作，确认无法继续才明确放弃。

## 接口与页面

`GET /api/v1/tasks/{taskId}/jobs` 保持 ApiResult 包装，节点增加 `title`、`dependsOn`、`skipReason`，`status` 使用三端一致枚举。标题来自固定计划的工作目标摘要，不返回内部上下文。

聊天页面以简单可折叠列表展示真实步骤、并行数量和复用标记；任务状态或已提交事件水位变化后读取节点，不加定时轮询。切换任务或组件退出后，迟到请求不得覆盖当前内容。读取失败提供“重新读取”。

接口支持可选 `planVersion`，响应携带 `planVersion`、`currentPlanVersion` 和 `acceptanceChecks`。页面可逐版查看过去的安排、返回当前安排；历史节点不混入当前完成数，旧版不显示当前版的验收结论。结果检查使用简单列表，区分程序检查、模型检查和用户确认。

当前展示真实计划节点与正式结果检查，文件读取、模型处理等细分活动尚未在这里完成。完整活动尝试历史及统一进度缓存仍属后续任务。

## 存储与恢复

沿用现有 Job VARCHAR 状态字段，无新增结构或实际库 DDL。SKIPPED 当前只有 DEPENDENCY_FAILED 一种原因；原因随 `job.skipped` 公开事件持久保存，查询按该唯一语义返回 skipReason。未来增加其他跳过原因时必须扩充存储和映射，不能沿用推断。

依赖状态更新和事件发布处于同一事务；更新带当前用户、目标、计划版本和原状态条件。旧计划迟到结果不推进新计划，重复失败不重复发布跳过事件。

## 统一完成规则实现（5.1）

`PlanJoinPolicyService` 已作为纯计算规则实现，接收当前计划版本、汇总策略、节点必要性与状态、待核对效果、必要验收结论及是否有可交付结果。旧版节点、重复身份、没有必要节点的计划直接拒绝。

| 情况 | 判断 |
| --- | --- |
| 任一必要或可选工作仍在运行、等待或恢复 | 等待工作收尾，不给任务结论 |
| 工作已停，但有交互或外部效果待核对 | 等待效果核对，不给任务结论 |
| 仍有依赖等待或恢复受限工作 | 交给 Master 协调，不给发布许可 |
| 全部收尾、必要工作成功、必要验收全部通过、有可交付结果 | 全部完成 |
| 全部收尾但必要工作失败、验收失败或未知，有可交付结果 | 部分完成 |
| 全部收尾，没有可交付结果 | 失败 |

ALL_REQUIRED 和 BEST_EFFORT 均遵守全部已接受分支先收尾的规则；BEST_EFFORT 允许收集失败分支后的可用结果，不把必要失败变成成功。可选失败不单独决定任务失败，仍按必要验收结论判断。空验收列表不能推断为已经通过。

`MasterSignalService`、完成候选提交和最终发布已共用这套规则。提交时保存逐项证据，原生回合结束准备发布时重新读取当前计划、工作与效果，避免候选保存后状态变化仍然发布。换计划在同一事务使旧候选失效；旧回合结束事件忽略，不能使新候选进入异常状态。

## 逐项验收与证据

计划条件结构为 `criterionId/text/required/verificationType`，程序检查可提供 `deterministicCheck`。条件固定在计划的 `definition_json`；旧字符串转换为必要的 MODEL_REVIEW，标记 `legacy=true`，不会产生历史通过结论。后端汇总策略和检查方式采用枚举，OpenAPI 与 TypeScript 同步。

| 检查方式 | 可信依据 |
| --- | --- |
| DETERMINISTIC | 平台内置 REQUIRED_RESULTS_READY 检查必要工作成功且结果已保存；未指定受支持检查器时为 UNKNOWN，不执行任意模型代码 |
| MODEL_REVIEW | Task Master 提交逐项 PASS/FAIL/UNKNOWN，必须引用当前计划成功 Job 的已保存结果；明确记录为模型判断 |
| USER_REVIEW | request_acceptance_review 从当前条件生成问题，经实际持久交互答复后核对 accepted；模型提交的 PASS 不能覆盖用户拒绝 |

用户确认固定目标、计划版本和条件摘要。完成候选中的 `acceptanceResults` 记录条件、检查人、证据引用、计划和目标修订；`acceptanceReviews` 保留待核实意见。缺少必要证据为 UNKNOWN，阻止全部成功。旧版确认或外部用户的结果引用会拒绝。

正式结束后只公开条件文字、检查方式与结论，不公开内部证据正文、会话或模型推理。结果尚未正式发布时不提前展示“已验收”。所有字段使用现有 JSON 存储，无新增表列或实际开发库 DDL。

`plan.published` 和 `job.reused` 在会话流保留白名单载荷，页面可接收并刷新步骤，不为这些通知重读整个会话。

## 验证边界

纯规则测试覆盖乱序链式依赖、等待恢复与明确失败的区别、并行分支隔离。隔离 MySQL 测试覆盖重复失败、明确放弃、未处理交互阻止放弃、计划替换与旧结果隔离；SDK 本地模型桩覆盖串行、并行和失败后部分交付。

模型桩不证明真实模型每次都能正确拆解任务。浏览器外观验收、完整故障恢复矩阵及全量回归应单独记录，不把组件测试或单次成功当作全部验收。
